Local Ranger policy benchmark measurements

These diagnostic measurements are not a production capacity or SQL latency SLA.
Hardware: Intel Xeon Platinum 8369B, 16 logical CPUs, shared host, no CPU pinning.
JVM: Oracle JDK 17.0.10, G1, Xms256m, Xmx12g, separate serial JVMs per variant.
Model: 5000 physical tables, 800 OR resource blocks per user, one SELECT policy
per user. Each block has catalog/database/table and three real columns plus
a user-named fourth column. The user-named column retains its Ranger meaning.
Request mix: seed83, 20 warmups, 120 samples, half allowed and half denied.
Requirement: ADMIN OR SELECT, global/catalog/database/table then three columns.
Initialization: actual RangerBasePlugin constructor, explicit model supplier V2.
User stores and context enrichers are disabled. No audit sink, Ranger HTTP
download, policy-cache disk IO, SQL planning/execution or login is measured.
Input generation is local and precedes installation. Peaks include generation,
installation and explicit GC. The refresh peak window also includes the two
revocation/new-grant checks; it is not a construction-only peak.
Different Ranger versions use their matching dependency classpaths. Compare
before/after within each version; cross-version changes are not isolated.

Measured optimized implementation: ef4721353bd. Unchanged stock results are
reused from the earlier serial stock runs after checking input, driver, native
library hashes and policy/audit fingerprints. Baselines and optimized results
were measured at different times on the shared host.
The standalone runner and its workload are in this directory. Use README.md
for portable setup and reproduction. The recorded numbers are one short batch;
tail percentiles need larger repeated runs for production capacity planning.

Interpretation and remaining costs
- Descriptor sharing reduces retained resource memory. Normalized HashMaps are
  reused to avoid an extra construction copy. Native
  evaluators, column resources and indexes still retain millions of blocks.
- Conservative scope pruning skips impossible parent SELF checks. Original
  Ranger still decides columns. The mixed workload speedup is not the same as
  the allowed-only speedup and must not be described as SQL execution speedup.
- Groups/roles, deny/exception, condition/validity, tag/zone, custom matching
  and audit-processor cases fall back. A default group policy can disable
  pruning for the whole service. Actual snapshot eligibility needs checking.
- Installation and full refresh are not guaranteed to become faster. Extra
  compaction work trades construction cost for retained heap and request cost.
- Peaks sampled every5ms are observed values, not safe heap capacity bounds.
  They exclude the rest of an FE and real download/JSON/audit/user-store costs.
- Installation seconds exclude the wider validation/retained-heap measurement
  window included in PreparationAndInstallSeconds fields in raw JSON output.
- Descriptor sharing is payload-local. Separate small deltas do not re-intern
  the entire retained engine and can reduce full-load sharing gains over time.
- The checked Ranger2.9 in-place delta mode changes permissions without
  advancing exposed service version. Summary version guards then fall back
  to native checks until a verifiable full replacement. Stock parity and
  revocation are covered; the formal full-refresh measurements use defaults
  with in-place updates disabled.
- The earlier MapN representation saved more retained heap but increased
  column-query allocation. It was replaced; these are corrected HashMap results.
- Each full-refresh pair verifies a revoked old table and a newly granted one.
  Policy/audit fingerprints and logical question counts agree before/after.
- A library-compatible run with Ranger2.8 is not a tested source backport or
  a binary plugin replacement for an older FE. Actual FE deployment, actual
  policy export, heap configuration and concurrent SQL remain separate checks.
- 3000 authorized principals do not specify 3000 concurrent SQL clients. The
  optimized allowed path still has substantial native column-matching cost.
- Queries during installation/summary rebuilding temporarily use native checks.
  Steady-request percentiles do not measure concurrent refresh-time SQL tails.
